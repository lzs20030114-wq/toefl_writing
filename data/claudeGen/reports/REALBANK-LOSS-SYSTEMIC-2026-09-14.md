# 真题丢题：从「逐个题型抢救」转成「全科度量 + 堵住共用的闸」（2026-09-14）

用户反馈：「各个题型都有普遍的丢题问题，真题哈。我之前进行了很多轮次的修复，但是显然这个问题仍然普遍。」

结论：**之前几轮修的都是对的，但修的位置太窄。** 丢题的主要机制是一条对所有题型都生效的闸，
而 09-13 那轮只把它给填词（CTW）开了口子；同时**丢题从来没有被度量过**，
所以每一轮都只能等用户撞见某一篇少题，再针对那个题型抢救一次 —— 换个题型照旧丢。

本轮做两件事：① 把那条闸对全部题型放开并让它自愈；② 建一张常驻的全科丢题账本 + 防退化闸。
本轮**不花 token、不改题库数据**：数据侧的回收要在本机跑（见 §5 跑法）。

## 2. 根因：一条对所有题型生效、却只给填词修过的闸

### 2.1 调用预算（`scripts/realbank/model_output.js`）

09-13 查清了 CTW「模型输出无法解析为 JSON」的真因：deepseek-v4-flash 是推理模型，
`max_tokens` 把推理 token 一起算，预算给小了推理会把正文吃光、返回空串。
于是 **ctw 的预算从 16000 提到 32000、超时从 90s 提到 300s**。

但当时的结论是「选择题的失败另有转写/分栏原因，别让它们顺手变贵」，所以
`ap / rdl / lcr / lc / la / lat / 修复轮` 全都留在 16000 / 90s。两条证据说明这个判断不成立：

1. 台账里 **531 次调用顶到 16000**，而 CTW 全部块历史上的调用数到不了这个量
   （每套 3 块 × ~70 套 ≈ 210 块，加两轮重跑也不够）→ 选择题块同样在顶预算；
2. 09-13 那轮 `--only-failed` **没改任何代码**原地重跑，165 个 flagged 块救回 81 块（≈50%）。
   确定性的「模型吐坏 JSON」不会靠重跑救回一半 —— 一半一半是预算/超时抖动的签名。

丢题路径：预算吃光 → 正文空或被截断 → 解析失败 → 块标 flagged → **从不进盲审 → 永远不进库**。

### 2.2 超时被当成系统性失败 → 一块慢，整卷白跑（`structure_set.mjs`）

`classifySystemicFailure` 把「请求超时」判为系统性失败，后果是
**整卷作废、不写产物、退出码 3 → `run_pipeline` 整批停**。
而按实测 ~230 token/s，16000 token 要跑 ~70s，紧贴 90s 的墙 ——
推理越长的块越容易撞上，**恰恰是最该救的那些块在拖垮整卷**。
（09-13 给 CTW 放宽超时时已经写明了这个机制，但只改了 CTW 一个题型。）

### 2.3 合流快照只存一次 → 听力救回来的题会被无声丢掉（本轮新发现）

两个来源的听力/口语合流都靠「从解析器原始产物出发」保证幂等，各自把 structure_set 的产物快照一份：

- 第一来源 `merge_first_source_asr.py` → `<卷>.structured.fs_parsed.json`
- 第二来源 `merge_vendor_asr.py` → `<卷>.structured.parsed.json`

两份都是**第一次合流时存一次，之后永不刷新**。所以：重跑 structure_set 把听力块从 flagged 救成 ok，
只写进 `structured.json`，下一次跑合流会从那份**陈旧快照**重建听力，刚救回来的块原样消失、一声不响。
仓库里对阅读已经有同一个坑的解法（`structured_io.syncReadingToBase`，头注写着
「任何就地修阅读的工具只写 structured.json 的话，下一次重跑合流就会被悄悄冲掉」），
但听力/口语从来没走过 structure_set 重跑，所以没人碰到。
**听力是全库丢题最多的一科，抢救恰好卡在这一步。**

### 2.4 元根因：没有账本

`sets.json` 里其实一直躺着全部证据（每套卷每个槽位 need/got），
但没有任何脚本/测试/后台页把它变成「缺口清单 + 归因」，也没有防退化闸。
所以：修完一个题型，没人知道别的题型缺多少；重建一次库，没人知道数字是涨是跌。
这就是「修了很多轮、问题依旧普遍」的结构性原因。

## 3. 本轮改了什么（代码侧，全部有测试）

| 文件 | 改动 |
|---|---|
| `scripts/realbank/model_output.js` | 预算按题型给全（选择题/修复轮 24000，default 也 24000，ctw 仍 32000）；**超时一律由 `budgetOf(maxTokens)` 从预算推导**，不许再手写（手写就会再配出一个撞墙组合）；新增 `retryBudget`；解析失败三分为 空 / **截断** / 真坏格式（`classifyBadOutput` + `isBudgetProblem`）—— 截断以前和坏格式报同一句话，正是 09-13 把 AP 的 70 道题误诊成格式病的原因 |
| `scripts/realbank/structure_set.mjs` | 所有要 JSON 的调用改走 `callForJson`：解析不出且失败签名是预算形，就**加倍预算自动重试一次**（成本只落在本来就已失败的块上，`max_tokens` 是上限不是账单）；选择题调用按题型取预算；merge 写回时带 `freshKeys` |
| `scripts/realbank/failure_policy.js`（新） | 失败分级抽成纯函数。**单块超时从硬失败降为软失败**：只记这一块 error（`--only-failed` 还能捡回来），累计 5 次才判为网络/服务侧故障中止。连接级 `ETIMEDOUT` 仍是硬失败 |
| `scripts/realbank/structured_io.js` | `writeStructured` 同时同步两份合流快照（只同步本次新产出的块，不拿合流结果回灌，幂等不破）；全量重跑路径打印提醒「这卷有合流快照，要重跑合流才生效」 |
| `scripts/realbank/loss_attribution.js`（新） | 丢题归因纯函数：按**额度**扣而不是按标签判（`duplicate_cluster` 这类纯溯源标记不认领任何缺题；`section_gap` 的额度就是 detail 里的「缺 N 题」；`ctw_answer_truncated` 只砍填词）；复核扣下按 scope 折成题数；整科缺席按蓝图补进分母，并按「管线覆盖这科吗 + 这卷跑过吗」拆成「跑了归零」（可扫）与「没跑过」（铺量决策）|
| `scripts/realbank/loss_ledger.mjs`（新） | 账本驱动：`data/realBank/loss-ledger.json`（1150 行缺口 + 123 项可执行补题任务）+ `--freeze` 写 `loss-baseline.json` |
| `__tests__/realbank-{loss-attribution,loss-guard,failure-policy}.test.js`（新）+ model-output / ctw-verify 扩充 | 共 +61 例 |

**防退化闸**：`__tests__/realbank-loss-guard.test.js` 拿 `data/realBank/loss-baseline.json`
卡住「重建一次库，某题型悄悄变少」—— 这正是过去几轮反复踩的坑
（补回更靠前的题让 id 改名、下架静默失效、合并把副本的题一起扔了）。
数字涨了要 `--freeze` 重冻；跌了测试直接红，必须先解释为什么跌。

## 4. 预期能捞回多少

账本里 **585 题「管线丢题」+ 359 题「整科跑了归零」= 944 题**，都是重扫 flagged 块的直接目标。
按 09-13 的实测命中率（原地重跑就救回 ≈50%，那还是**没有**加预算、没有自动重试的情况），
再叠加本轮的预算放开 + 预算形自动重试 + 超时不再整卷作废，这批的回收率应当明显高于 50%。

另外 **2096 题**标着「整科没跑过」，全是听力（1755）与口语（341）——
`run_pipeline` 的 `SECTIONS` 锁死在 `reading,writing` 造成的覆盖空白。
这一桶要先分清源料：BACKLOG 记着「听力无音频 18 套 = 源缺」，剩下约 21 套听力有音频。
**这一桶没动，因为它涉及要不要给听力/口语铺量、花多少钱，是你拍板的事**（见 §6）。

## 5. 本机怎么跑（数据侧回收）

云端这台容器没有 `.codex-tmp/realbank/`（中间产物只在你本机），也没有 API key，所以数据侧一步都没跑。
本机按这个顺序：

```bash
# 0. 先看账本，确认要扫哪些卷（零成本，随时可跑）
node scripts/realbank/loss_ledger.mjs --top 40
#    ① 那张表就是「立刻能回收的」清单，97 套·科

# 1. 阅读/写作：扫 flagged 块（新预算 + 自动重试 + 超时不再整卷作废）
node scripts/realbank/structure_set.mjs "<卷名>" --only-failed --sections reading,writing
#    先挑账本里缺口最大的几卷试跑，看日志里「预算重试」救回多少再铺开

# 2. 听力/口语：同样扫，然后**必须重跑合流**，否则救回的块进不了库
node scripts/realbank/structure_set.mjs "<卷名>" --only-failed --sections listening,speaking
#    日志会打印「已同步合流快照 …」——看到这行才说明 §2.3 那个坑绕过去了
python scripts/realbank/merge_first_source_asr.py --all      # 第一来源
# 或 python scripts/realbank/merge_vendor_asr.py ...          # 第二来源

# 3. 落库 + 装卷 + 重算账本
node scripts/realbank/build_bank.mjs
node scripts/realbank/assemble_sets.mjs
node scripts/realbank/loss_ledger.mjs --freeze       # 数字涨了就重冻基线
npx jest __tests__/realbank-loss-guard.test.js       # 确认没有哪个题型反而变少
```

花费：只对已经失败的块重跑，且只在失败签名是预算形时才多一次重试。
跑之前用 `--dry` 看块数，按台账口径估价（`node scripts/ops/deepseek-usage-report.mjs` 对账）。

**顺手可验证 §2.1 的推断**：台账里顶到 16000 的那 531 次调用，按题型拆一下
（`.ops/deepseek-usage.jsonl`）。如果非 CTW 占大头，就实锤了「选择题也一直在顶预算」。

## 6. 建议（按做的顺序）

### 第一步：先把 944 题捞回来 —— 不需要拍板，成本极小

只对**已经失败的块**重跑，且只在失败签名是预算形时才多一次重试。按账本 ① 的清单从缺口最大的
几卷开始，跑法见 §5。做完重跑账本 + `--freeze` + `npx jest __tests__/realbank-loss-guard.test.js`。

优先级建议：**先写作（4.5 / 3.23 / 4.28 那批）**。理由不是它最大，而是它最卡：
学术讨论全库只有 7 题，是整卷拼齐的唯一瓶颈，而这一桶里就有 24 题 disc + 24 题 email；
且写作不碰音频、不用重跑合流，链路最短、最容易验证新预算是否真的在救题。
写作跑通、确认「预算重试」确实在日志里救回东西，再铺到阅读（ctw 为主）和听力。

### 第二步：听力/口语铺量 —— 建议**先只铺一套试水，不要整批铺**

2096 题里听力占 1755。别急着整批跑，原因是成本结构不对称：文本生成走订阅边际≈0，
**听力的钱全在 TTS 配音**，而且 `run_pipeline --all` 有已知的烧钱坑（会把月份文件夹当卷跑）。
建议：挑 1 套**确认有音频**的卷，走 `structure_set --sections listening,speaking` +
合流 + 配音，实测单套花多少、盲审过多少，再拿这个数字决定剩下 20 套铺不铺。
一套的代价是几块钱，买到的是一个能外推的单价。

### 第三步：`SECTIONS` 放开 —— 建议**现在不动**

放开等于把听力纳入常规产线：每次铺量自动带上听力与 TTS 成本，而 `--only-failed` 直接调
`structure_set --sections listening,speaking` 已经够用，放开只省几行命令。
等第二步的实测单价和盲审通过率出来，再决定要不要把它变成默认。

（`AP over_cap 11 道`是 09-13 的残余项，与本轮无关，仍挂 BACKLOG。）
